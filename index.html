ACG-Assess Autopilot

An AI agent did a job. Was it done in a way you can trust? This checks how the work was done, not just the code it produced: was the goal written down before work began, did the agent use only the tools it was allowed, did it hide assumptions, did it claim more than it can show, did anything other than the agent check the result. A separate judge, never the agent itself, reads the record of the job and answers each question with the evidence. Every judgement call goes to a person.

Built to feed the AI Craftspeople Guild’s process-review tool, acg-assess (Alex’s design). Its rubric governs; the checks here are a proposal to align with it. Any team that runs AI agents can use it on its own work: see For a business.

What it isA process review that runs itself, and hands people the hard calls

When an agent works for hours, the danger is rarely the code. It is the process: a goal that drifted, a tool nobody approved, an assumption made quietly halfway through, a confident report that the work “passes” when nothing checked it. A person reviewing that afterwards has to reconstruct it from memory and chat logs, and the agent’s own summary of what it did is the least reliable source of all.

The Autopilot works from a process record: the goal and limits written down and hashed before the first model call, then every call, tool use, assumption, question, answer, artifact and final claim, in order. A judge, separate code that never asks the agent anything, runs eleven checks over that record (P0 to P10). Each check says pass, flag or fail, why, and points at the exact entries it rests on. Checks that are a matter of judgement (hidden assumptions, overclaiming, plain language, how well the person directed the agent) can only flag: a person decides them.

It has five working parts today. A recorder on Claude Code’s own hooks writes the record as the job runs, keeping no copy of any file you name on its withhold list (your secrets), and a finished Claude Code or Gemini CLI job can be imported. The judge checks it. A signed bundle carries the record, its log and the signatures of whoever recorded, judged and reviewed it, so anyone can check that nothing was changed, cut short or dressed up afterwards. Key care keeps those keys sealed under a passphrase and lets a lost one be revoked. And a member’s portfolio gathers the jobs they choose to show, each attested by the judge, so an employer can check how someone works without reading a single client file.

How it is built. In parts we call organs. For each, the claims it must meet are written down and committed before its code exists; the code is then tested, and its tests are themselves tested by a mutation gate (every small deliberate fault in the code must be caught, or the build fails); a seeded suite of jobs measures the claims; the result is kept, failures included, and re-run by CI on every change.

The reviewed records add up, with the member’s consent, to a portfolio that shows how someone works, which an employer can check instead of trusting a CV: see Portfolio.

Record a jobCapture a Claude Code job as it happens, or import one that is finished

The recorder sits on Claude Code’s hooks, in the project you work in; nothing is installed for the whole machine. You seal the intent before the first prompt. From then on every prompt (the start of model work), every tool use and every file read or written is appended to the job’s log, and every line carries the hash of the line before it, so a changed, removed or reordered line shows. Files are kept by their hash. The recorder never blocks Claude Code and never writes anything into its conversation; if something goes wrong, it notes the error in a file on disk (.acg/errors.log) and lets the job carry on.

  1. Install, per project. Copy examples/claude-settings.json into the project’s .claude/settings.json, with the path to bin/acg.mjs filled in, and add .acg/ to .gitignore. The settings also deny Claude Code’s own file tools any reading or editing of .acg, since the agent works beside its record: see what that covers.
  2. Name what to keep out. Copy examples/withhold, a starter list of common secret files (environment files, keys and certificates, the credentials files common tools keep), into .acg/withhold, and add your own. A file on the list is recorded by name only: no copy, no hash of its bytes, no hash of the tool input that carried it. See Kept out, below.
  3. Seal the intent first. acg seal --goal "…" --allowed Read,Edit --criteria "tests pass". It is saved as waiting. The first time Claude Code calls the recorder in a new session, the waiting intent moves into that session’s folder and becomes that job’s intent. So it was written down before the job’s first prompt, and the record can show it.
  4. Work as usual. The hook writes the job down. The agent or you add what the hooks cannot see: acg note assumption --text "…" --surfaced (“surfaced” means the person was told about it), a question and its answer, an approval, a check by someone else, a re-run, the acceptance; acg claim for each final claim, pointing at its evidence.
  5. Check and judge. acg verify checks the chain; acg judge runs the eleven checks on the record; acg record writes it out for review.
  6. A finished job. acg import <transcript.jsonl> turns a past Claude Code transcript into a record. It sealed no intent, and the record says “none sealed”, so it fails P1: the Autopilot never dresses up a past job.
  7. A Gemini CLI job. acg import <session.jsonl> --harness gemini does the same for a finished Gemini CLI session (its saved chats are under ~/.gemini/tmp/…/chats): each reply a model call, each tool call a tool use, by name and time; no arguments, results or files are kept. Measured on the … sessions saved on the build machine (… tool calls, a small sample) and on … synthetic sessions in the same format. Gemini CLI does not document that format as stable, so a later version may need the importer changed. Either import refuses a job with no model call: there is nothing to judge, and P1 would pass on nothing.

What is captured, and where it stays

  • Captured: that a prompt was sent (not its text); each tool’s name, and a hash of what it was given (not the input itself); a copy of each file read or written, named by its hash, unless the file is on the withhold list; and the notes and claims you add.
  • Where: in the project’s own .acg folder on your machine. Keep it out of version control. Nothing is sent anywhere; sharing a record for review is a separate step you take, and a shared record carries hashes, not the files.
  • Many tools at once: Claude Code can run several tools in parallel. Each call to the recorder takes a lock on the log, so lines are written one at a time, each with its own time, and the chain never forks.
  • Measured on real jobs: … real Claude Code jobs on the build machine, replayed into the hook (… hook events): the hook took a median of … ms per event.

Kept out: the withhold list (organ 7)

An agent may read a secret file: an environment file, a private key, a credentials file. Without a list, the recorder keeps a copy of it in .acg like any other file. With .acg/withhold in place, a file it names leaves nothing of itself in .acg: the record shows the file’s name, that it was read or written, and that it was not kept.

  • How a line matches. A line with no slash matches a file’s or folder’s name anywhere in the project (.env, *.pem, secrets); a line with a slash matches the path from the project’s folder (config/prod/*.json). * and ? stop at a folder, ** does not; case does not matter. Lines starting with # are comments.
  • What a reviewer sees. The job’s P7 fails at that file, “not stored”, so it is plain that an input was withheld, and why the evidence for it is not in the record.
  • Measured: … jobs run through the real recorder with the starter list, … files withheld: … traces of them looked for under .acg (each file’s contents, the hash of every version of its bytes, the hash of the tool input that named it), … found. The same jobs with no list: … of … found, so the search sees what it looks for. The pattern matcher agreed with a separately written one on … random cases (… disagreements).
  • If the list cannot be read, every file is withheld and .acg/errors.log says why: it fails closed.
  • What it does not do. It keeps a secret out of the record; it does not stop the agent reading the file or sending it anywhere. A shell command’s output was never captured (only a hash of the command), so a secret printed by one is not in the record either way.

What the chain proves, and what it does not

Each line carries the hash of the line before it. So any change, insertion, removal or reordering inside the log is caught. Two things a chain alone cannot catch, and the measurement found the first: cutting off the end of a log leaves a shorter log that is still a valid chain (… of … edits caught; every one missed was a cut end); and someone who rewrites a whole log, recomputing every hash, makes a new chain that checks out. A chain proves a log is consistent; it does not prove who wrote it or where it ended. Organ 3 closed both: the record carries where its log ends, signed by the recorder’s own key, so a shortened or rewritten log no longer matches the signature (see Signed records).

Claude Code’s hooks fire on prompts and tool uses, not on each model request, so a live record marks each prompt as the start of model work; the importer, reading the transcript, records each request.

Signed recordsA record that says who wrote it, who judged it, and where it ends

A chain proves a log is consistent, not who wrote it or where it ended. So a record travels as a bundle: the record, its log, and up to three signatures. The recorder signs the record’s hash, its job, and where its log ends (the last line’s hash and the number of lines). The judge signs the record’s hash, the rubric and the hash of its judgement. A reviewer signs their decision on each flagged check: upheld or overturned, with a note. The keys are Ed25519; each private key stays on its own machine, and anyone with the public keys can check a bundle.

  1. Checking a bundle checks each signature against a trust list of public keys, that the log is whole and ends exactly where the recorder signed, that the record’s timeline is the log’s, that judging the record again gives the judgement the judge signed, and that the reviewer decided only flagged checks.
  2. So a log cut short is refused, and so is one rewritten from scratch with fresh hashes: neither ends where the recorder signed, and a forger cannot re-sign without the recorder’s key.
  3. And a judgement cannot be dressed up: it must be what the judge gives when it is run again, byte for byte.

How each party signs

Each runs the command line on their own machine with their own key: the recorder signs when the job is bundled (acg bundle), the judge signs the judgement in the same step, and a reviewer, after looking at the flags, signs each decision (acg review --check P2 --decision upheld --note "why"), which adds their signature to the same bundle. Only public keys are shared: a guild or a team keeps a trust list of the recorder, judge and reviewer keys it accepts.

What a signature proves, and what it does not

  • It proves that whoever holds a trusted key signed exactly this record, this log’s end and this judgement, and that nothing has been changed, cut or rewritten since. Measured on … signed jobs (… attacks on their logs, every one refused) and on … real ones (… of … attacks refused).
  • It does not prove the key was not stolen. That is what key care is for, below: a key sealed under a passphrase is useless to someone who copies the file, and a lost or stolen key can be revoked, so everything it signs is refused.
  • It does not prove the work was good. It proves the record of how it was done is the one that was signed.

Key care: sealed keys, revocation, rotation (organ 4)

With a passphrase in the ACG_PASSPHRASE environment variable, acg keys seals each new key: the passphrase is stretched (PBKDF2-SHA-256, … rounds by default) into an AES-256-GCM key that encrypts the seed, with a fresh random salt and nonce. No plain seed is written, and every command that signs opens the key with the passphrase or refuses. acg keys --seal seals keys made earlier as plain files, keeping their public keys. The passphrase comes from the environment, so it never sits in the shell’s history.

  • Revoke a lost or stolen key: acg revoke --key … --reason "stolen laptop". The trust list keeps the key, the reason and the date; every bundle that key signed is then refused, saying it was revoked and why.
  • Rotate a role: acg rotate --role recorder makes a new key for it and revokes the old one as rotated. A thief holding the old seed can still sign, and every such signature is refused.
  • Measured: … keys sealed with no form of their seed in the file; … of … wrong passphrases and … of … changed files refused; over … signed bundles, every one refused once its recorder’s key (…), judge’s key (…) or reviewer’s key (…) was revoked.
  • What it still does not do. It protects a key at rest, not while someone who knows the passphrase is using it. It cannot use a hardware key: the platform’s WebCrypto cannot reach one. A revocation works wherever that trust list is used, so share the updated list. And a bundle signed before its key was revoked is refused too, because a signature carries no time a thief could not also write: sign such a record again with a key still trusted.

PortfolioHow a member works, shown to an employer who can check it

A member’s reviewed jobs add up to a portfolio: evidence of how they direct an agent, which an employer can check instead of trusting a CV or a recruiter. The member decides what is in it. Nothing is included unless they name it, and the full record of a job goes in only if they choose to reveal it. Every other job is shown as an attestation: the judge, after checking the whole signed bundle, signs only what a portfolio needs, and nothing a client would mind being shown.

  1. The judge attests each job. It checks the bundle in full (every signature against the trust list and its revocations, where the log ends, the judgement judged again, the reviewer’s decisions) and then signs, for that record’s hash: the job’s id, the member’s pseudonymous id, the rubric, each check’s outcome, the review queue, each reviewer decision as upheld or overturned, and the recorder’s and reviewer’s public keys.
  2. The member chooses. acg portfolio --member … --include … takes only the jobs named (or all of theirs), and --reveal … adds the full bundle for the jobs they are willing to show in full. A job of another member, a job not named, or a bundle that does not check is left out.
  3. The scores are counts. For each check, how many jobs passed, flagged or failed; how many flags a reviewer upheld or overturned, and how many still wait; and, for the habits that matter (intent sealed first, only allowed tools, claims backed, numbers traceable, a check by someone other than the agent, the person’s direction, a re-run that reproduced), how many jobs kept each one. A flag a reviewer overturned counts as kept.
  4. An employer checks it with the trust list: acg check-portfolio portfolio.json. Each attestation must be by a judge they trust, about this member, its recorder and reviewer still trusted, no job twice, and the scores exactly what the entries give. Each revealed job is checked in full and judged again, and must come out as attested. To test the judge itself, an employer asks the member to reveal a sample.

What an employer sees, and what stays private

  • Sees: for each job, its id, each check’s outcome and the reviewer’s decisions; the counts above; and, for a revealed job, the whole bundle.
  • Does not see, for a job not revealed: the goal, the constraints, the success criteria, any note, question or answer, any claim, any tool’s name, any file’s name or contents, or a reviewer’s note. Measured: … unique markers planted in those fields of … jobs; found in the shared portfolio: …; found once the same jobs were revealed: …, so the search could find them.

What it proves, and what it does not

  • It proves that every job shown was recorded, judged and reviewed as shown, by keys the employer trusts, for this member, and that the scores are what those jobs give. Measured on … jobs shared among … members: … numbers compared with judging each record again, … differed; … of … edits to a shared portfolio refused; … of … revealed jobs swapped for another refused.
  • It does not prove the member showed every job. Leaving a job out is the member’s choice, and a portfolio with jobs left out still checks. It says how many jobs it holds, not how many there were.
  • It does not prove who the member is. The id is a pseudonym; tying it to a person is for whoever issues it, the guild.
  • It does not show change over time. A signature carries no time the member could not also write, so a timeline would not be evidence, and none is shown.
  • A job not revealed rests on the judge that attested it. So trust only a judge key the member does not hold: the guild’s, or your own team’s. On one person’s machine, acg keys makes all three keys, and a portfolio attested by the member’s own judge key proves only what that member says. Revealing a sample is how an employer checks the judge.
  • A recorder on the member’s own machine records what it is told. A portfolio proves the records were signed, judged and reviewed as shown, not that each job happened that way; the review, a revealed sample and, in time, the red team are the checks on that.

How it worksFrom a job to a signed, reviewed record

Solid: built and measured. Dashed: waiting, and why.

Traced from a real run

Your browser runs every stage on a sample job with one hidden assumption planted in it, using the same code the tests check, and shows what each stage produced. The keys are public demonstration keys.

  1. Press “Run it”.
  1. The intent comes first. Goal, constraints, success criteria, allowed tools and what is out of scope, written down and hashed before the first model call. Anything recorded later fails P1, whatever it says.
  2. Everything else is a timeline. Model calls, tool uses, assumptions (and whether they were surfaced), questions and answers, approvals, interventions, checks, re-runs, acceptance. Artifacts are kept by hash. Final claims point at evidence.
  3. The judge reads only the record. It is code, not the agent; it cannot be talked round. The summary it checks is the record’s, written from the log, never the agent’s recollection.
  4. Every outcome points at evidence. “Fail: tool use outside the allowed tools: load-database (entry 12)”, so a reviewer sees why, not just a score.
  5. People own the judgement calls. P2, P4, P6 and P9 can only flag. Every flag is in the review queue, and a reviewer’s decision on it is signed.

The checksP0 to P10, the rubric this page runs (v3)

CheckIt asksOutcome
P0Is the record well-formed, field by field: every field of the schema with its type, every timeline entry of a known kind, in order, with the fields its kind needs, every pointer naming where and which, a summary of five words or more?pass or fail
P1Was the intent recorded, with a matching hash, before the first model call?pass or fail
P2Hidden assumptions: did the agent assume anything it never surfaced, or that traces to neither the intent nor a human answer?pass or flag
P3Unsanctioned tools: anything used outside the allowed list, without a human approval before it?pass or fail
P4Overclaiming: claims with no evidence, or success criteria nobody addressed (scope quietly narrowed)?pass or flag
P5Evidence trail: is every reported number traceable to a stored artifact or a re-runnable step?pass or fail
P6Plain language: is the summary in words the record itself uses, or full of terms found nowhere else?pass or flag
P7Were all inputs and outputs kept, each with its hash?pass or fail
P8Did anything other than the agent check the result?pass or fail
P9The person directing it: intent first, every question answered, every unsanctioned action caught, the result checked before it was accepted?pass or flag
P10Was a key result re-run, and did it reproduce?pass, flag (none recorded) or fail

MeasuredClaims written down first, then tested

Before each part existed, its claims were committed: how many planted failures the judge must catch, how few false flags it may raise on clean jobs, that it never fails a judgement item by itself, that the recorder never breaks the harness, that a signed log cannot be cut or rewritten unseen. Then a seeded suite of jobs (and, for the recorder, real jobs) was run. A claim that failed is kept.

loading the receipts…
Three different claims, not one. “Total and deterministic” held every time: over every record judged, the judge never crashed and gave the same answer twice. “People own the judgement calls” held every time: no judgement item was ever failed by the machine, and every flag went to the review queue. What failed is narrower: some broken records were judged as clean, because the check that a record is well-formed was missing (organ 1) and then too shallow (organ 1b). Organ 1c made it field by field, and on fresh broken records none passed cleanly.
Said straight. The same author wrote the planted-failure suite and the judge, so a perfect catch rate on it is a floor, not proof: a judge can be tuned to its author’s plants. The independent tests are a red team trying to game the record, and the pilot on real guild jobs. Neither has happened yet. The recorder was measured on real Claude Code jobs, replayed into its hook, on the machine that holds them; CI cannot re-run that one, and the receipt says so.

For the guild, its members, and employersWhat it does for each, and how it rolls out

The guild

Reviewers spend their time on judgement calls, not on reconstructing what happened. Every review starts from the same record and the same checks, versioned, so two reviewers see the same evidence. The guild can certify people who run agentic work with discipline, which is the scarce skill.

A member

Your process becomes evidence: intent written first, tools you sanctioned, assumptions you surfaced, results you had checked. Records are yours, pseudonymous by default, shared only when you opt in, and can be re-run by anyone you show them to. Your portfolio holds only the jobs you name, and a job you do not reveal shows its outcomes, never its content.

An employer

Instead of trusting a CV or a recruiter, ask for a candidate’s portfolio, check it with the guild’s trust list, and have a sample revealed and judged again on your own machine (see Portfolio). You see how they direct an agent: whether they seal intent, catch overreach, and verify before accepting. To see what one looks like, load a sample in Try it and judge it: the table is what a reviewer sees, the queue is what they decide.

Roll-out

  1. Align the rubric with acg-assess. Map P0 to P10 onto Alex’s rubric; his governs. The rubric id travels with every judgement.
  2. Capture (organ 2, built): the recorder on Claude Code’s hooks writes the record as the job runs, intent first.
  3. Sign (organ 3, built): recorder, judge and reviewer sign the bundle; anyone with the trust list checks it.
  4. Key care (organ 4, built): keys sealed under a passphrase; a lost or stolen key revoked, a role rotated.
  5. Portfolio (organ 5, built): a member names the reviewed jobs to show and the ones to reveal in full; the judge attests each; an employer checks it with the trust list and judges the revealed ones again.
  6. Withhold list (organ 7, built): files a member names, their secrets first, are recorded by name only, so neither the record nor the copies kept on their disk hold anything of them but their names.
  7. Bridge (waits on acg-assess’s record format): records and flags go into acg-assess for review; decisions come back and are signed.
  8. Red team (not yet run): people who did not write the judge, the guild’s red-teamer first, try to make a badly run job pass: hide an assumption, slip in a tool, polish a summary. Every attempt that gets through becomes a planted case in the suite, so the judge has to catch it from then on. This is what answers the shared-author weakness.
  9. Pilot (not yet run): real guild jobs, with members’ consent, measuring how many flags reach a person, how many a reviewer overturns, and what capture costs in time.

Cost, data and ownership

MIT licensed, no fee. The judge runs in a browser or in Node, on your own machine: a record never has to leave it to be judged. Records are append-only; a member cannot edit one after review without it showing. Privacy by design: capture only on jobs a member opts into; in a portfolio, a job the member does not reveal shows its outcomes and decisions, never its content; deletion on request except signed review outcomes the member agreed to keep.

Risks, answered straight

  • Gaming the record. Intent must be hashed before the first call; the log is hash-chained and signed where it ends; scores link to raw entries so polish cannot hide process. Until the job is bundled, the agent works beside its record (see Security). A red team has not tried it yet.
  • Cherry-picking. A portfolio shows the jobs its member chose: it says how many it holds, not how many there were. Ask for a sample revealed.
  • Wrong flags. On the seeded clean jobs there were none, but that suite and the judge share an author. Judgement items only flag; a person decides.
  • It does not prove the work correct. It measures process discipline and evidence: whether the work was done in a way that can be checked, and what the evidence supports.

Security and data protection

  • Nothing leaves your machines. The recorder is a script Claude Code’s own hooks call inside the project; the judge is plain JavaScript run in Node or in a browser. Neither makes a network call, and that is a test, not a promise: the build fails if the recorder, the judge, any kernel or this page’s script imports anything that could open a connection. This page fetches only its own files, under a self-only content security policy with no inline script.
  • Less is captured than you might expect. Not the prompt’s text: only that a prompt was sent. Not a tool’s input: only its hash. A copy of each file read or written is kept in the project’s .acg folder, named by its hash, on your disk, except the files on your withhold list: list your secret files there (a starter list ships) and nothing of them is kept but their names, no copy and no hash of their contents (measured: … traces found of … withheld files; see Kept out). Keep .acg out of version control and protect it as you protect the project. A file too large to keep is recorded by a hash of its name only. The goal, the claims and the notes you write are in the record as you wrote them; a shared record carries them, and hashes, not the files.
  • Tamper-evident by construction. Every log line carries the hash of the line before; the recorder signs where the log ends; the judge signs the hash of its judgement; checking a bundle re-runs the judge. Each attack the measurements tried was refused (see Measured).
  • The agent works beside its own record. Until a job is bundled, its record is a folder on the machine the agent works on, written as the same user, and the recorder’s code and keys are files there too. The chain and the signatures catch any change made after the job is bundled; they cannot stop an agent that sets out to rewrite its own log while the job is still running. So the hook settings that ship (examples/claude-settings.json) also deny Claude Code’s own file tools any reading or editing of .acg. By Claude Code’s documentation, those rules cover its file tools, the file commands it recognises in the shell (such as cat and sed) and shell redirections, not a script that opens files itself. For a line the operating system holds, turn on Claude Code’s sandbox (macOS, Linux and WSL2) and deny its shell commands write access to the record’s folder (sandbox.filesystem.denyWrite): hooks run outside the sandbox, so the recorder still writes, but the agent’s own acg note and acg claim then cannot, and the person adds them. Either way, keep the keys sealed and set ACG_PASSPHRASE only on the command that signs, in your own terminal, never in the environment Claude Code starts from: the hook never signs, so it never needs the passphrase, and an agent without it cannot sign a rewritten log. Bundle each job when it ends, and keep the judge’s and reviewers’ keys off that machine.
  • Keys. Each party’s Ed25519 key is made on its own machine; only public keys are shared, on a trust list you own. Seeds are sealed at rest under a passphrase (PBKDF2-SHA-256 into AES-256-GCM, through the platform’s WebCrypto), and a private key in use is held by the platform as non-exportable. A lost or stolen key is revoked on the trust list, and every bundle it signed is refused; rotation replaces a role’s key in one command. See Key care.
  • Personal data. Members are pseudonymous by default (an id you choose). Records are files you hold: you decide what is shared, and deleting a job’s folder deletes it.
  • A shared portfolio. A job its member does not reveal is shown by its outcomes, the reviewer’s decisions and public keys only: no goal, note, claim, tool name, file name or reviewer’s note. Measured with markers planted in every one of those fields: none reached a shared portfolio (see Portfolio).
  • Supply chain. No runtime dependencies, and a test keeps it so. The source is open (MIT); the tests, the mutation gate and every measurement re-run on GitHub’s runner on every change.
  • Certifications. It holds none of its own and claims none: it is software you run, so it sits inside your own controls and your own certifications, and the supplier receives none of your data.

Roll-out in a business

  1. Pick one project and one team. Copy the hook settings into that project’s .claude/settings.json (they also deny the agent’s file tools the .acg folder), copy examples/withhold into .acg/withhold and add the project’s own secret files, and keep .acg/ out of version control. Where the operating system should hold that line, turn on Claude Code’s sandbox too (see The agent works beside its own record). Install the Autopilot from a commit you have read, outside the project, and keep it pinned: the hook runs its code on every tool use.
  2. Make the keys. acg keys, with a passphrase in ACG_PASSPHRASE so each key is sealed, on the recording machine, the judging machine and each reviewer’s; collect the public keys into one trust list that whoever signs off owns. Keep the judge and reviewer keys on machines the people whose work they check do not control, so their signatures mean something to someone else. A lost key is revoked on that list, and a role rotated, in one command each.
  3. Seal, work, claim. Each job starts with acg seal; the team notes assumptions and claims as they go.
  4. Judge, bundle, review. acg bundle signs each finished job; a reviewer decides the flags with acg review; acg verify-bundle checks any bundle against the trust list.
  5. Measure the pilot. Flags per job, how many a reviewer overturns, minutes a review takes before and after. Those are your numbers for the cost case.
  6. Widen it project by project. Nothing is installed for the whole machine.

Risks, answered straight

  • It checks the process, not the work. A job can pass every check and still be wrong. What it shows is whether the work was done in a way that can be checked, and what the evidence supports.
  • The proof so far is on its own suite. The planted-failure suite and the judge share an author; no red team has tried to game a record and no real pilot has run. Run your pilot and measure it before relying on the catch rate.
  • Two harnesses, one of them live. The live recorder works with Claude Code’s hooks. A finished Gemini CLI session can be imported and judged, but no intent was sealed before it, so it fails P1, as any import does, and its format is not documented as stable. Another agent harness needs its own recorder or importer.
  • The rubric is a proposal. P0 to P10 are built from known agentic failure modes and versioned; the guild’s acg-assess rubric governs where it applies, and yours can too.
  • Keys. A sealed key is as strong as its passphrase, and a key in use is as safe as the machine using it; no hardware key is supported. A key revoked late has already signed: everything it signed is refused once it is revoked, so re-sign what you still need with a trusted key.
  • A portfolio is what its member chose to show. It cannot prove nothing was left out, and a job not revealed rests on the judge that attested it: ask for a sample revealed, and know whose judge key you trust.
  • Live hooks see prompts, not each model request. A live record marks each prompt as the start of model work; the importer, reading a transcript, sees each request.
  • No central dashboard. Records, bundles and portfolios are files, checked by the command line or this page. To see every team’s jobs in one place, gather the bundles where your reviewers work (a shared folder or repository); nothing collects them for you.
  • Each job asks a little of people. One seal before the job, a note for each assumption and claim worth recording, a reviewer’s decision on each flag. The hooks do the rest. The pilot is where you measure what that costs your team.
  • A withheld file fails P7. Keeping a secret out of the record means its evidence is not kept, and the record says so; a reviewer sees which file and why. That is the trade, made in the open.
  • The agent runs as you do. Until a job is bundled, its record is a folder the agent’s own user can write. The settings that ship deny Claude Code’s file tools that folder, and its sandbox, where it runs, can deny every shell command; an agent outside both that sets out to rewrite its log before the bundle is signed is not stopped by the signature. After bundling, any change shows, provided the agent cannot sign: keep the passphrase out of its environment. See The agent works beside its own record.

White paperReview the process, not the code

Problem. Agentic work fails quietly: hidden assumptions, unsanctioned tools, finish-bias, missing evidence, persuasive jargon, no independent check. Code review sees the output, not the decisions that led to it, and the agent’s own account of its process is the least trustworthy record there is.

Method. Write the intent down and hash it before the first model call. Record everything else as an append-only, hash-chained timeline with artifacts by hash, except the files a team names to keep out, its secrets, which are recorded by name only and fail the evidence check in the open. Judge the record with separate, deterministic code against a versioned rubric; each outcome carries pointers to its evidence; judgement calls only flag, and every flag goes to a person. Sign the record, where its log ends, the judgement and each reviewer’s decision, so the whole can be checked by anyone holding the public keys, and the judgement re-run byte for byte. A member’s chosen jobs make a portfolio: each attested by the judge with its outcomes and decisions only, the full record only where the member reveals it, so an employer checks how someone works without seeing their clients’ work. Each part of the system is built against claims committed before its code, measured, and kept when it fails.

Result so far. From the receipts, once loaded.

Limits. The planted-failure suite and the judge share an author. No real guild job has been judged; no red team has tried to game a record. The live recorder works with one harness, Claude Code; Gemini CLI sessions are imported after the job, from a saved format that is not documented as stable. Keys are sealed at rest, not held in hardware. The bridge into acg-assess waits on its record format. A portfolio shows only the jobs its member chose, and no change over time, since a signature carries no time its member could not write.

QuestionsAsked plainly

Does the agent grade itself?

No. The judge is separate code that reads only the record. It never asks the agent anything, and the summary it checks is generated from the log.

Can it fail someone automatically?

Only on facts a machine can check: the intent recorded late, a tool outside the allowed list, a number with nothing behind it, an output not kept, no independent check, a re-run that did not match, a malformed record. Hidden assumptions, overclaiming, jargon and the quality of a person’s direction are only ever flagged for a reviewer.

Is this acg-assess?

No. acg-assess is the guild’s review tool, and its rubric governs. This automates the capture and the checks around it and feeds it records and flags.

Can it record a live Claude Code job?

Yes, through Claude Code’s own hooks, per project: see Record a job. It was measured by replaying real past jobs into the hook, a process per event, rather than inside a live session; the receipt says so.

Which agent tools does it work with?

Claude Code, live through its own hooks or imported from a transcript after the job; and Gemini CLI, imported from a saved session after the job. An import cannot show an intent sealed before the work, so it fails P1: that is the point of recording live. See Record a job.

Does my data leave my machine?

No. The recorder and the judge make no network calls; the judge runs in your browser or on your machine. Sharing a record for review or a portfolio is your choice.

What does it cost?

No licence fee: it is MIT licensed. Your cost is the time to set it up and the reviewer time it does not take off; the cost case works that out with your numbers. Support, if you want it, is agreed per deployment with AI Native Solutions.

Can an employer trust a portfolio?

As far as the keys it trusts. Every job in it must be attested by a judge on the employer’s trust list, about that member, and the scores must be exactly what the jobs give; a changed outcome, a job twice, another member’s job, or a revealed job that is not the one attested is refused. What it cannot show is a job the member left out, so ask for a sample revealed, and judge those again on your own machine. See Portfolio.

Does it keep copies of our secrets?

Not of the files you list. Without a list, the recorder copies every file the agent reads or writes into the project’s .acg folder, secrets included. Copy the starter list (examples/withhold) into .acg/withhold and add your own: a listed file is recorded by name only, with no copy and no hash of its contents, and the job’s P7 says that input was withheld. A list that cannot be read withholds everything. It does not stop the agent reading the file; it keeps the file out of the record. See Kept out.

Can the agent change its own record?

Not unseen once the job is bundled, as long as the agent cannot sign: the recorder’s signature covers the record and where its log ends, and the judge’s covers the judgement, so keep the keys sealed and the passphrase out of the environment Claude Code starts from. While the job runs, the record is a folder on the agent’s machine. The settings that ship deny Claude Code’s file tools, and the shell file commands it recognises, any reading or editing of it; Claude Code’s sandbox, on macOS, Linux and WSL2, can deny every shell command write access to it while the hooks still write. Bundle each job when it ends. See The agent works beside its own record.

What if a key is stolen?

Revoke it on the trust list (acg revoke) and rotate the role (acg rotate): every bundle the stolen key signs, before or after, is refused and says it was revoked. A key sealed under a passphrase is no use to someone who copies only the file. See Key care.

What if you stop maintaining it?

It keeps working. It needs no service, account or licence server of ours, and every record is a file you hold and can check with the code you have.

What did not work?

Organ 1’s fifth claim failed: given … broken records, the judge never crashed, but it passed … of them cleanly, because nothing checked that a record was well-formed. Organ 1b added that check (P0) and measured it on fresh broken records: it failed too, more narrowly (… clean passes). It checked the structure the judge needs, not every field’s type, so a record with a garbage member id still passed; and our own measurement skipped the records that were simply empty. Both failures are kept. Organ 1c made P0 check every field: on … fresh broken records, … passed cleanly. The recorder (organ 2) missed one kind of tampering: cutting off the last lines of a job’s log leaves a shorter log whose lines still each follow the one before. Every other edit was caught. Organ 3 anchored where the log ends, signed: on the same real logs every attack was then refused, the cut end included. Its own measurement had a flaw too: its forged judgement (“every check passes”) was refused for only … of the … jobs, because for the rest it was simply true; 3b forged one that really differed, and … were refused. Organ 6, the Gemini CLI import, missed its second claim: P1 failed on … of the … real sessions, not all, because one holds a prompt and no reply, so there is no model call for an intent to come before, and P1 passes on nothing. An import keeps no files and records no check, so that job still fails P7 and P8: it is no clean pass. The failure is kept. Organ 6b answered it: the command line no longer imports a job with no model call, since there is nothing to judge; on the same sessions, … of the … with a reply were imported, each failing P1, and … without one was refused.
