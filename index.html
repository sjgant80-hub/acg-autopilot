ACG-Assess Autopilot

An AI agent did a job. Was it done in a way you can trust? This checks how the work was done, not just the code it produced: was the goal written down before work began, did the agent use only the tools it was allowed, did it hide assumptions, did it claim more than it can show, did anything other than the agent check the result. A separate judge, never the agent itself, reads the record of the job and answers each question with the evidence. Every judgement call goes to a person.

Built to feed the AI Craftspeople Guild’s process-review tool, acg-assess (Alex’s design). Its rubric governs; the checks here are a proposal to align with it.

What it isA process review that runs itself, and hands people the hard calls

When an agent works for hours, the danger is rarely the code. It is the process: a goal that drifted, a tool nobody approved, an assumption made quietly on step 40, a confident report that the work “passes” when nothing checked it. A person reviewing that afterwards has to reconstruct it from memory and chat logs, and the agent’s own summary of what it did is the least reliable source of all.

The Autopilot works from a process record: the goal and limits written down and hashed before the first model call, then every call, tool use, assumption, question, answer, artifact and final claim, in order. A judge, separate code that never asks the agent anything, runs ten checks over that record. Each check says pass, flag or fail, why, and points at the exact entries it rests on. Checks that are a matter of judgement (hidden assumptions, overclaiming, plain language, how well the person directed the agent) can only flag: a human reviewer decides them in acg-assess.

How it is built. In parts we call organs. For each, the claims it must meet are written down and committed before its code exists; the code is then tested, and its tests are themselves tested by a mutation gate (every small deliberate fault in the code must be caught, or the build fails); a seeded suite of jobs measures the claims; the result is kept, failures included, and re-run by CI on every change. Organ 1 is the record and the judge; organs 1b and 1c added and then tightened the check that a record is well-formed.

The reviewed records add up, with the member’s consent, to a portfolio that shows how someone works, which an employer can check instead of trusting a CV.

Start hereThree minutes

  1. Load a sample record in Try it: a clean job, or a job with one failure planted in it.
  2. Judge it. Your browser runs the same judge the tests and the mutation gate check. Nothing is sent anywhere.
  3. Read the results. Each check shows pass, flag or fail, the reason, and the entries it points to. Flags are listed as the review queue: what a person must decide.
  4. Paste your own record in the same box to judge it. The format is in the blueprint.
  5. Check the receipts in Measured: the claims written down before the judge was built, and what happened.

Record a jobCapture a Claude Code job as it happens, or import one that is finished

The recorder sits on Claude Code’s hooks, in the project you work in; nothing is installed for the whole machine. You seal the intent before the first prompt. From then on every prompt (the start of model work), every tool use and every file read or written is appended to the job’s log, and every line carries the hash of the line before it, so a changed, removed or reordered line shows. Files are kept by their hash. The recorder never blocks Claude Code and never writes anything into its conversation; if something goes wrong, it notes the error in a file on disk (.acg/errors.log) and lets the job carry on.

  1. Install, per project. Copy examples/claude-settings.json into the project’s .claude/settings.json, with the path to bin/acg.mjs filled in, and add .acg/ to .gitignore.
  2. Seal the intent first. acg seal --goal "…" --allowed Read,Edit --criteria "tests pass". It is saved as waiting. The first time Claude Code calls the recorder in a new session, the waiting intent moves into that session’s folder and becomes that job’s intent. So it was written down before the job’s first prompt, and the record can show it.
  3. Work as usual. The hook writes the job down. The agent or you add what the hooks cannot see: acg note assumption --text "…" --surfaced (“surfaced” means the person was told about it), a question and its answer, an approval, a check by someone else, a re-run, the acceptance; acg claim for each final claim, pointing at its evidence.
  4. Check and judge. acg verify checks the chain; acg judge runs the eleven checks on the record; acg record writes it out for review.
  5. A finished job. acg import <transcript.jsonl> turns a past Claude Code transcript into a record. It sealed no intent, and the record says “none sealed”, so it fails P1: the Autopilot never dresses up a past job.

What is captured, and where it stays

  • Captured: that a prompt was sent (not its text); each tool’s name, and a hash of what it was given (not the input itself); a copy of each file read or written, named by its hash; and the notes and claims you add.
  • Where: in the project’s own .acg folder on your machine. Keep it out of version control. Nothing is sent anywhere; sharing a record for review is a separate step you take, and a shared record carries hashes, not the files.
  • Many tools at once: Claude Code can run several tools in parallel. Each call to the recorder takes a lock on the log, so lines are written one at a time, each with its own time, and the chain never forks.

What the chain proves, and what it does not yet

Each line carries the hash of the line before it. So any change, insertion, removal or reordering inside the log is caught: in the measurement, every such edit was. Two things are not caught yet, and the measurement found the first. Cutting off the end of a log leaves a shorter log that is still a valid chain. And someone who rewrites a whole log, recomputing every hash, makes a new chain that checks out. A chain proves a log is consistent; it does not prove who wrote it or where it ended. Organ 3 fixed both: the record now carries where its log ends, signed by the recorder’s own key, so a shortened or rewritten log no longer matches the signature (see Signed records).

Claude Code’s hooks fire on prompts and tool uses, not on each model request, so a live record marks each prompt as the start of model work; the importer, reading the transcript, records each request.

Signed recordsA record that says who wrote it, who judged it, and where it ends

A chain proves a log is consistent, not who wrote it or where it ended. So a record travels as a bundle: the record, its log, and up to three signatures. The recorder signs the record’s hash, its job, and where its log ends (the last line’s hash and the number of lines). The judge signs the record’s hash, the rubric and the hash of its judgement. A reviewer signs their decision on each flagged check: upheld or overturned, with a note. The keys are Ed25519; each private key stays on its own machine, and anyone with the public keys can check a bundle.

  1. Checking a bundle checks each signature against a trust list of public keys, that the log is whole and ends exactly where the recorder signed, that the record’s timeline is the log’s, that judging the record again gives the judgement the judge signed, and that the reviewer decided only flagged checks.
  2. So a log cut short is refused, and so is one rewritten from scratch with fresh hashes: neither ends where the recorder signed, and a forger cannot re-sign without the recorder’s key.
  3. And a judgement cannot be dressed up: it must be what the judge gives when it is run again, byte for byte.

Try it: sign a sample, then tamper with it

Your browser builds a bundle from a sample job and signs it with three public demonstration keys (never real ones), then checks it. Each button tampers with a copy and checks again.

From the command line: acg keys makes this machine’s three keys (the private seeds stay in .acg/keys), acg bundle signs a job, acg review --check P2 --decision upheld --note "…" adds a reviewer’s decision, acg verify-bundle checks one.

How it worksFrom a job to a reviewed record

  1. The intent comes first. Goal, constraints, success criteria, allowed tools and what is out of scope, written down and hashed before the first model call. Anything recorded later fails P1, whatever it says.
  2. Everything else is a timeline. Model calls, tool uses, assumptions (and whether they were surfaced), questions and answers, approvals, interventions, checks, re-runs, acceptance. Artifacts are kept by hash. Final claims point at evidence.
  3. The judge reads only the record. It is code, not the agent; it cannot be talked round. The summary it checks is the record’s, never the agent’s recollection.
  4. Every outcome points at evidence. “Fail: tool use outside the allowed tools: load-database (entry 12)”, so a reviewer sees why, not just a score.
  5. People own the judgement calls. P2, P4, P6 and P9 can only flag. Every flag is in the review queue.

The checksP0 to P10, the rubric this page runs (v3)

CheckIt asksOutcome
P0Is the record well-formed, field by field: every field of the schema with its type, every timeline entry of a known kind, in order, with the fields its kind needs, every pointer naming where and which, a summary of five words or more?pass or fail
P1Was the intent recorded, with a matching hash, before the first model call?pass or fail
P2Hidden assumptions: did the agent assume anything it never surfaced, or that traces to neither the intent nor a human answer?pass or flag
P3Unsanctioned tools: anything used outside the allowed list, without a human approval before it?pass or fail
P4Overclaiming: claims with no evidence, or success criteria nobody addressed (scope quietly narrowed)?pass or flag
P5Evidence trail: is every reported number traceable to a stored artifact or a re-runnable step?pass or fail
P6Plain language: is the summary in words the record itself uses, or full of terms found nowhere else?pass or flag
P7Were all inputs and outputs kept, each with its hash?pass or fail
P8Did anything other than the agent check the result?pass or fail
P9The person directing it: intent first, every question answered, every unsanctioned action caught, the result checked before it was accepted?pass or flag
P10Was a key result re-run, and did it reproduce?pass, flag (none recorded) or fail

MeasuredClaims written down first, then tested

Before the judge existed, its claims were committed: how many planted failures it must catch, how few false flags it may raise on clean jobs, and that it never fails a judgement item by itself. Then a seeded suite of jobs was built and judged. A claim that failed is kept.

loading the receipts…
Three different claims, not one. “Total and deterministic” held every time: over every record judged, the judge never crashed and gave the same answer twice. “People own the judgement calls” held every time: no judgement item was ever failed by the machine, and every flag went to the review queue. What failed is narrower: some broken records were judged as clean, because the check that a record is well-formed was missing (organ 1) and then too shallow (organ 1b). Organ 1c made it field by field, and on fresh broken records none passed cleanly.
Said straight. The same author wrote the planted-failure suite and the judge, so a perfect catch rate on it is a floor, not proof: a judge can be tuned to its author’s plants. The independent tests are a red team trying to game the record, and the pilot on real guild jobs. Neither has happened yet. Organ 1 judges records; capturing them from a live agent is organ 2.

For the guild, its members, and employersWhat it does for each, and how it rolls out

The guild

Reviewers spend their time on judgement calls, not on reconstructing what happened. Every review starts from the same record and the same checks, versioned, so two reviewers see the same evidence. The guild can certify people who run agentic work with discipline, which is the scarce skill.

A member

Your process becomes evidence: intent written first, tools you sanctioned, assumptions you surfaced, results you had checked. Records are yours, pseudonymous by default, shared only when you opt in, and can be re-run by anyone you show them to.

An employer

Instead of trusting a CV or a recruiter, sample a candidate’s reviewed records and re-run them. You see how they direct an agent: whether they seal intent, catch overreach, and verify before accepting. To see what one looks like, load a sample in Try it and judge it: the table is what a reviewer sees, the queue is what they decide.

Roll-out

  1. Align the rubric with acg-assess. Map P0 to P10 onto Alex’s rubric; his governs. The rubric id travels with every judgement.
  2. Capture (organ 2, built): the recorder on Claude Code’s hooks writes the record as the job runs, intent first. A second harness is still to do.
  3. Bridge (organ 3): records and flags go into acg-assess for review; decisions come back and are signed.
  4. Red team (not yet run): people who did not write the judge, the guild’s red-teamer first, try to make a badly run job pass: hide an assumption, slip in a tool, polish a summary. Every attempt that gets through becomes a planted case in the suite, so the judge has to catch it from then on. This is what answers the shared-author weakness.
  5. Pilot (not yet run): real guild jobs, with members’ consent, measuring how many flags reach a person, how many a reviewer overturns, and what capture costs in time.
  6. Portfolio: opt-in, redacted samples an employer can re-run.

Cost, data and ownership

MIT licensed, no fee. The judge runs in a browser or in Node 20+, on your own machine: a record never has to leave it to be judged. Records are append-only; a member cannot edit one after review. Privacy by design: capture only on jobs a member opts into, client data hashed or redacted in a portfolio, deletion on request except signed review outcomes the member agreed to keep.

Risks, answered straight

  • Gaming the record. Intent must be hashed before the first call; records are append-only; scores link to raw entries so polish cannot hide process. A red team has not tried it yet.
  • Wrong flags. On the seeded clean jobs there were none, but that suite and the judge share an author. Judgement items only flag; a person decides.
  • It does not prove the work correct. It measures process discipline and evidence: whether the work was done in a way that can be checked, and what the evidence supports.

White paperReview the process, not the code

Problem. Agentic work fails quietly: hidden assumptions, unsanctioned tools, finish-bias, missing evidence, persuasive jargon, no independent check. Code review sees the output, not the decisions that led to it, and the agent’s own account of its process is the least trustworthy record there is.

Method. Write the intent down and hash it before the first model call. Record everything else as an append-only timeline with artifacts by hash. Judge the record with separate, deterministic code against a versioned rubric; each outcome carries pointers to its evidence; judgement calls only flag, and every flag goes to a person. Each part of the system is built against claims committed before its code, measured, and kept when it fails.

Result so far. From the receipts, once loaded.

Limits. The planted-failure suite and the judge share an author. No real guild job has been judged; no red team has tried to game a record; capture, the bridge and the portfolio are not built yet.

QuestionsAsked plainly

Does the agent grade itself?

No. The judge is separate code that reads only the record. It never asks the agent anything, and the summary it checks is generated from the log.

Can it fail someone automatically?

Only on facts a machine can check: the intent recorded late, a tool outside the allowed list, a number with nothing behind it, an output not kept, no independent check, a re-run that did not match, a malformed record. Hidden assumptions, overclaiming, jargon and the quality of a person’s direction are only ever flagged for a reviewer.

Is this acg-assess?

No. acg-assess is the guild’s review tool, and its rubric governs. This automates the capture and the checks around it and feeds it records and flags.

Can it record a live Claude Code job?

Yes, through Claude Code’s own hooks, per project: see Record a job. It was measured by replaying real past jobs into the hook, a process per event, rather than inside a live session; the receipt says so.

Does my data leave my machine?

Not to be judged: the judge runs in your browser or on your machine. Sharing a record for review or a portfolio is your choice.

What did not work?

Organ 1’s fifth claim failed: given 2,000 broken records, the judge never crashed, but it passed some of them cleanly, because nothing checked that a record was well-formed. Organ 1b added that check (P0) and measured it on fresh broken records: it failed too, more narrowly. It checked the structure the judge needs, not every field’s type, so a record with a garbage member id still passed; and our own measurement skipped the records that were simply empty. Both failures are kept. Organ 1c made P0 check every field: on 2,000 fresh broken records, none passed cleanly. And the recorder (organ 2) missed one kind of tampering: cutting off the last lines of a job’s log leaves a shorter log whose lines still each follow the one before. Every other edit was caught. Organ 3 anchored where the log ends, signed: on the same 31 real logs every attack was then refused, the cut end included. Its own measurement had a flaw too: its forged judgement (“every check passes”) was simply true for 550 of the 1,000 jobs, so it was rightly accepted; 3b forged one that really differed, and all 1,000 were refused. See Measured.
